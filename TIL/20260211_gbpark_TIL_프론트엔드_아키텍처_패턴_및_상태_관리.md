# TIL (Today I Learned)

## 📚 학습 주제
소프트웨어 아키텍처 패턴 (모듈화, DDD, 클린 아키텍처) 및 상태 관리 (클라이언트/서버 상태, React Query) 💡

---

## 🔑 핵심 내용
-   **체계적인 모듈/컴포넌트 구조:** 시스템을 `app`, `processes`, `pages`, `widgets`, `features`, `entities`, `shared` 등으로 계층화하고 `public.api`를 통해 캡슐화하여 비즈니스 로직과 UI의 명확한 분리, 독립적 개발, 예측 가능한 의존성을 목표로 합니다.
-   **도메인 주도 설계 (DDD) 원칙:** 복잡한 도메인을 `Bounded Context`로 나누고 `Ubiquitous Language`를 사용하여 공통 언어를 구축하며, `Entity`, `Value Object`, `Aggregate`, `Repository`, `Domain Service`와 같은 전술적 설계 요소로 도메인 모델을 구현합니다.
-   **클린 아키텍처의 목표:** 프레임워크, 데이터베이스, UI 등 외부 기술적 세부사항으로부터 핵심 비즈니스 로직을 보호하고, `의존성 역전 설계`를 통해 유연하고 유지보수하기 쉬운 시스템을 구축합니다.
-   **클라이언트/서버 상태의 구분:** 애플리케이션의 상태를 브라우저 내에서만 관리되는 `클라이언트 상태`와 서버에 저장되어 비동기적으로 접근하는 `서버 상태`로 명확히 구분하여 효율적인 상태 관리를 가능하게 합니다.
-   **React Query 활용:** 서버 상태 관리를 위한 강력한 라이브러리로, 캐싱, 중복 요청 통합, 백그라운드 업데이트, 데이터 유효성 관리 등 다양한 기능을 제공하여 서버 데이터 처리를 최적화합니다.

## 📝 상세 내용

### 🏗️ 모듈/컴포넌트 구조 및 원칙
소프트웨어 시스템을 구성하는 주요 요소들의 역할과 구조에 대해 학습했습니다. 이는 비즈니스 로직과 UI를 명확히 분리하고, 기능 단위의 독립적인 개발을 가능하게 하며, 예측 가능한 의존성 흐름을 만듭니다.

-   **`app`**: 전역 설정 및 애플리케이션의 시작점을 담당합니다.
-   **`processes`**: 회원가입과 같이 여러 페이지에 걸쳐 동일한 사용자 흐름을 담당하는 단위입니다.
-   **`pages`**: 브라우저 주소(URL) 단위로 구성되는 컴포넌트입니다.
-   **`widgets`**: 독립적인 UI 요소 또는 특정 기능의 묶음입니다.
-   **`features`**: '등록(regist)', '검색(search)'과 같은 동사 행위, 즉 비즈니스 기능을 묶은 단위입니다.
-   **`entities`**: '사용자(user)', '장바구니(cart)', '게시물(post)'과 같은 데이터, 즉 비즈니스 엔티티를 나타냅니다.
-   **`shared`**: 여러 곳에서 재사용 가능한 유틸리티나 공통 컴포넌트 등을 포함합니다. 이는 `layers - slices - segments`와 같은 계층적 모듈화의 가장 낮은 세그먼트 깊이에 해당합니다.

```javascript
// shared 컴포넌트 활용 예시
import { useForkFeaturesApi } from 'features/fork';
import { useForkEntitiesModel } from 'entities/fork';
import { Button, Icon } from 'shared/ui'; // shared에서 Button과 Icon을 가져옴

function SomeComponent() {
  const forkFeatures = useForkFeaturesApi();
  const forkEntities = useForkEntitiesModel();

  return (
    <Button
      onClick={forkFeatures.api.fork}
      icon={<Icon type="fork" />} // shared.icon.fork 와 같은 방식으로 사용
      data={forkEntities.model.forkCount}
    >
      Fork
    </Button>
  );
}
```

-   **`public.api`**: 외부로 공유하고 싶은 `index.ts` 파일을 생성하여 모듈의 외부 노출 영역을 관리합니다. 이는 캡슐화를 통해 직접적인 내부 의존성을 방지하는 중요한 메커니즘입니다.

### 🏛️ 도메인 주도 설계 (DDD: Domain Driven Design)
복잡한 도메인을 효과적으로 모델링하고 관리하기 위한 접근 방식입니다.

-   **전략적 설계 (Strategic Design)**
    -   **Bounded Context (경계가 있는 컨텍스트)**: 복잡한 도메인을 이해하고 시스템 전체의 경계를 나누는 단위입니다. 예를 들어, 동일한 '사용자'라도 결제 시스템에서는 '구매자', CS 시스템에서는 '민원인'으로 다른 모델을 가질 수 있습니다.
    -   **Ubiquitous Language (보편적 언어)**: 기획자, 디자이너, 개발자 등 모든 팀 구성원이 도메인에 대해 동일한 용어를 사용하도록 약속하는 것입니다 (예: 장바구니에 담는 행위를 `addToCart`로 통일).

-   **전술적 설계 (Tactical Design)**
    -   **Entity**: 고유한 ID를 가지는 데이터 객체 (예: `User`, `Post`). 상태가 변하더라도 ID가 같으면 동일한 객체로 간주됩니다.
    -   **Value Object**: ID가 없으며, 값 자체가 중요한 객체입니다 (예: `Color(red)`). 불변성을 가지며, 값의 동일성으로 객체를 비교합니다.
    -   **Aggregate**: 관련 있는 Entity와 Value Object들의 묶음으로, 데이터 일관성을 유지하며 함께 움직이는 단위입니다 (예: 장바구니 수정 시 장바구니 전체의 일관성 유지).
    -   **Repository**: 데이터를 저장하거나 가져오는 창구 역할을 합니다 (예: `fetchUser(id)`).
    -   **Domain Service**: 특정 Entity나 Value Object에 속하지 않으면서 여러 도메인 객체에 걸쳐 복잡한 비즈니스 로직을 수행하는 함수 또는 클래스입니다 (예: 유저와 쿠폰 정보를 조합하여 최종 할인액을 계산).

### 🛡️ 클린 아키텍처 (Clean Architecture)
비즈니스 로직을 외부 세계(프레임워크, 데이터베이스, UI, 외부 API 등 변경 가능성이 높은 기술적 세부사항)로부터 보호하는 아키텍처 패턴입니다.

-   **핵심 원칙**: 비즈니스 로직이 외부 기술에 의존하지 않도록 `의존성 역전 설계`를 적용합니다.
-   **구조**:
    -   **Entities**: 핵심 비즈니스 규칙(Enterprise Business Rules)을 포함하는 최상위 레이어입니다.
    -   **Use Cases**: 애플리케이션의 핵심 기능들을 구현하는 레이어로, 엔티티를 사용하여 특정 비즈니스 로직을 처리합니다.
    -   **Interface Adapters**: 외부 세계(UI, DB, Web)와 내부 비즈니스 로직 사이의 변환 계층입니다. 유스케이스와 엔티티가 이해할 수 있는 형태로 데이터를 변환하고, 반대로 내부 데이터를 외부 시스템이 원하는 형태로 내보냅니다.

### 🔄 클라이언트 상태와 서버 상태
애플리케이션에서 관리하는 상태를 두 가지 주요 유형으로 구분하여 이해합니다.

| 구분           | 클라이언트 상태 (Client State)                                                                                                                   | 서버 상태 (Server State)                                                                                                                  |
| :------------- | :----------------------------------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------- |
| **정의**       | 사용자의 브라우저나 기기 내에만 존재하는 정보. 서버와 통신할 필요가 없으며, 앱이 닫히거나 새로고침되면 사라지는 경우가 많음.                        | 서버에 저장되어 있고 여러 사용자가 공유할 수 있는 정보. 클라이언트가 이 데이터를 보려면 반드시 비동기 API를 통해 요청해야 함.             |
| **소유권**     | 전적으로 클라이언트(UI)에 있음.                                                                                                                  | 원격 서버에 있음.                                                                                                                         |
| **접근 방식**  | 동기적으로 접근 가능.                                                                                                                            | 비동기적으로 가져옴.                                                                                                                      |
| **변화 가능성**| 클라이언트 내에서 관리되며, 서버와의 독립성이 높음.                                                                                             | 데이터가 로컬에 저장된 후에도 서버에서 변경될 수 있음 (스냅샷 형태로 특정 시점 데이터 보존 가능).                                          |
| **예시**       | 모달 창이 열려 있는지 여부, 입력 폼에 입력 중인 텍스트, 다크/라이트모드 테마 설정, 리스트의 필터링 조건. | DB에 저장된 사용자 프로필 정보, 게시글 목록 및 댓글, 장바구니에 담긴 상품 목록.                                                           |

### 📸 스냅샷
원본 데이터는 계속 변하더라도, 특정 시점의 데이터를 고정하여 기록해두는 용도로 사용됩니다. 이는 데이터의 일관성을 보장하거나 특정 시점의 상태를 보존할 때 유용합니다.

### ⚛️ React Query
서버 상태를 효율적으로 관리하기 위한 강력한 라이브러리입니다.

-   **주요 기능**:
    -   **캐싱**: 이전에 가져온 데이터를 캐시하여 불필요한 네트워크 요청을 줄입니다.
    -   **중복 요청 통합**: 동일한 데이터에 대한 여러 요청을 단일 요청으로 통합하여 서버 부하를 줄입니다.
    -   **백그라운드에서 오래된 데이터 업데이트**: 사용자에게 즉시 데이터를 보여주고, 백그라운드에서 최신 데이터를 가져와 업데이트합니다.
    -   **데이터 유효성 관리**: 데이터가 얼마나 오래되었는지(stale) 알 수 있어, 적절한 시점에 데이터를 갱신합니다.
    -   **데이터 업데이트 즉시 반영**: 데이터 업데이트 시, UI에 가능한 빠르게 반영되도록 돕습니다.
    -   **성능 최적화**: 페이지네이션 및 데이터 지연 로드와 같은 복잡한 시나리오를 효과적으로 처리하여 성능을 최적화합니다.
    -   **메모리 및 가비지 수집 관리**: 서버 상태의 메모리 사용 및 가비지 수집을 효율적으로 관리합니다.
    -   **구조 공유**: 쿼리 결과를 메모화하여 불필요한 렌더링을 방지합니다.

## 💡 새롭게 알게 된 점
소프트웨어 개발에서 복잡성을 관리하고 유지보수성을 높이기 위해 다양한 아키텍처 패턴(DDD, 클린 아키텍처)과 모듈화 전략이 필수적임을 다시 한번 깨달았습니다. 특히, `Bounded Context`나 `public.api`를 통한 캡슐화가 실제 프로젝트에서 어떻게 의존성을 줄이고 팀 생산성을 높일 수 있는지 구체적으로 이해하게 되었습니다. 또한, `클라이언트 상태`와 `서버 상태`를 명확히 구분하고 `React Query`와 같은 도구를 활용하는 것이 대규모 애플리케이션의 상태 관리 효율을 극대화하는 핵심 요소임을 명확히 인식했습니다.

## 🤔 궁금한 점 / 추가 학습 필요
-   각 아키텍처 패턴(DDD, 클린 아키텍처, Feature-Sliced Design과 유사한 모듈 구조)을 실제 프로젝트에 적용할 때의 장단점 및 적합한 상황에 대한 심층적인 비교 연구가 필요합니다.
-   `Domain Service`와 `Application Service`의 정확한 역할 분담 및 구현 방법에 대해 더 깊이 탐구하고 싶습니다.
-   React Query의 `Mutation` 및 `Optimistic Update` 기능과 같은 고급 활용법에 대해 자세히 학습해야겠습니다.
